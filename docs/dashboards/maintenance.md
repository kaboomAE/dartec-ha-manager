# Maintenance: what each choice costs across Home Assistant updates

Home Assistant ships a release every month. The fleet takes approved releases
automatically, through guarded updates (agent 0.19.0: bench approval, backup,
health check, rollback). Every dashboard dependency is something that can make
a home look broken the morning after an update, even though the update itself
reported healthy. The health check does not look at dashboards.

## Cost by choice

| Choice | What it is | Breaks on HA updates? | Cost per HA release | Verdict for customer homes |
|---|---|---|---|---|
| **Built-in cards** (sections, tile, heading, area, thermostat, button, clock, entity-filter) | Home Assistant's own frontend | Rarely. HA announces card changes in the release notes and keeps backward compatibility for YAML. One change in 2026.4, auto height with a 24 px row gap, shifted spacing without breaking anything | Read the release notes' frontend section; take one screenshot per prototype on the bench (R13) | **Use** |
| **Built-in dashboards** (Overview/Home, Lights, Climate, Security) | Generated by HA from areas and floors | No. HA regenerates them | None. They only need correct areas and floors, which the manager already applies | **Use as the free baseline** |
| **A theme using only documented variables** (`primary-color`, `accent-color`, `state-*-color`) | YAML in `config/themes`, applied as CSS variables | No. These are the only variables HA calls supported | None | **Use** |
| **A theme using internal variables** (`ha-card-background`, `ha-font-family-body`, `--md-*`, `--mdc-*`) | The same, but using variables HA calls "unsupported" | Silently. A renamed variable reverts to HA's default, so colours drift or the font changes. 2025.5 removed every `paper-*` variable at once, and four themes on the cloudapp.dev list still compute to white-on-white today | One look per release at the six theme screenshots | Acceptable for Dartec's own theme, with a short list of internal variables we test. Pin third-party themes to a version |
| **card-mod** | JavaScript that injects CSS into cards | **Yes, now.** Issues [#606](https://github.com/thomasloven/lovelace-card-mod/issues/606), [#616](https://github.com/thomasloven/lovelace-card-mod/issues/616), [#617](https://github.com/thomasloven/lovelace-card-mod/issues/617) report failures on 2026.8 and 2026.9. The last release was v4.2.1 on 2026-02-08, and the HA-LCARS theme has moved away from it | Unbounded: every HA frontend change can break a selector | **Do not install** |
| **Custom cards** (Mushroom, Bubble Card, button-card, and others) | JavaScript modules loaded into the homeowner's browser | Sometimes. Each has its own release schedule. The cloudapp.dev author calls a button-card dashboard maintainable only by the person who built it | A test and a pinned version per card, per HA release | **Not by default.** Only with the owner's approval, for a named reason |
| **Custom dashboard strategies** (Dwains Dashboard Next) | JavaScript that builds a whole dashboard | **Yes, already.** Three upstream bugs on HA 2026.7 and later ([#18](https://github.com/dwainscheeren/dwains-dashboard-next/issues/18), [#19](https://github.com/dwainscheeren/dwains-dashboard-next/issues/19), [#20](https://github.com/dwainscheeren/dwains-dashboard-next/issues/20)) cost three agent releases (0.21.0 to 0.21.2) of workarounds in `www/dashboard-fix.js` | High. We now maintain patches against someone else's code | **Stop offering to new homes** (R11) |
| **HACS kiosk-mode** (`?kiosk`) | JavaScript that hides HA's toolbar and sidebar | Possible with each frontend change | A test per release | Not used. The owner ruled HACS out for panels, and panels work without it |
| **Fully Kiosk Browser** | A paid Android browser app with an official HA integration | The integration is maintained in HA core. The app updates on its own schedule | A licence per tablet, and app updates | A documented fallback only |

## Risky dependencies for a fleet, and why

Themes are YAML and become CSS variables, so they cannot run code. Everything
below **runs JavaScript in the homeowner's browser, or in Home Assistant
itself**. That code can read anything the signed-in person can see, and it
can call any service they can call. None of it is reviewed by Home Assistant.
HACS says so, and the cloudapp.dev HACS guide repeats it.

What makes these risky for a **fleet** rather than for one hobbyist:

- **One maintainer, many homes.** Most of these are one person's spare-time
  project. If they stop, or accept a bad contribution, every Dartec home that
  took the update has it.
- **The latest release by default.** The manager's HACS installs take HACS's
  `available_version`. That is fine for a theme. For JavaScript it means an
  untested release reaches every home at the next rollout. The agent's
  downgrade guard prevents going backwards, not forwards.
- **Updates are not staged by us.** A HACS frontend update is not part of
  guarded updates' test-then-roll-out ring.
- **GitHub device login.** Installing HACS itself needs an interactive GitHub
  authorisation per home. The fleet already rotates one token across homes
  (`hacs_token_set`).

**The rule this guide proposes (owner to confirm):** nothing that runs code
goes to a customer home without the owner's approval of that repository and
that exact version. Each approved dependency then gets:

1. a pinned version in the manager's catalogue;
2. a bench test on each HA release before the fleet takes that release;
3. a named person at Dartec who owns it.

Today, only the agent itself and Dwains meet the "runs code" bar. Dwains is
unpinned.

## A per-release routine (15 minutes, on the bench)

After a new HA release is approved for the bench, and before the fleet takes
it:

1. Rebuild the test villa and the prototypes from
   [prototypes/](prototypes/), using the calls in `bench-log.jsonl`.
2. Take the screenshot set (phone, tablet, wall, NSPanel; light and dark; EN
   and AR) and compare it with the previous release's. Look for spacing,
   colours, and anything blank or unavailable.
3. Open the Dartec theme in both modes.
4. Remove everything again, and compare the bench with its baseline.

Recommendation R13 turns steps 1–2 into an automated check in this
repository's CI, which already runs real HA containers
([HANDOVER.md §4](../../HANDOVER.md#4-ci)).

## Themes: pinning and applying

- Install through HACS with an exact `version`. The bench did this for every
  theme, and it works (`hacs/repository/download` with `version`).
- Apply with `frontend.set_theme` (`name` and `name_dark`). This is the system
  default, and it survives restarts.
- Since 2026.2, **a person's own theme choice overrides the system default**,
  per person, across their devices. Leave panel accounts' theme unset, so they
  follow the default.
- Keep the Dartec theme to documented variables where possible. Test the few
  internal ones each release: `ha-card-background`, `ha-font-family-body`.
